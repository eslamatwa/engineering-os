1. Plugin, Not a Skill

A skill can tell Claude what to do. Only a plugin can stop a tool call that breaks the rules.

Skill only

  • Instructions loaded into context when relevant.
  • Rules are requests. The model can skip or misread them.
  • No hooks: no gate, no approval capture, no ledger.

Plugin

  • Subagents, commands and hooks in one install.
  • Hooks run as code on matching tool calls.
  • Can't ship permission rules itself, so /engos:init offers them for the project.

The session summary, refusals and briefs carry the know-how. Hooks carry the guarantees.

2. Threat Model

Decided: the plugin guards against honest mistakes and a model misled by text it read. It does not try to contain a model that is deliberately working around it.

In scope

  • Editing a sensitive file while thinking the change is trivial.
  • Pushing, publishing or deleting without asking.
  • Claiming "tests pass" without running them.
  • Following instructions planted in a README, log or web page.

Out of scope for v0.1

  • A model deliberately writing protected files through scripts.
  • Anything outside the repo that Bash touches indirectly.
  • OS sandbox, tamper-proof ledger, confirmation codes.

The README states this plainly: the plugin prevents common mistakes and detects indirect changes inside the repo after they happen. It is not a sandbox.

Gate (PreToolUse) and Observe (PostToolUse) run on every write, Bash and Agent call from step 02 to 07, inside subagents too. A crashed or missing hook blocks.

5. What Is Actually Enforced

Three honest levels instead of yes / no.

prevented

Code stops it before it runs. The target is known for sure.

detected

Code finds it after it ran, from the git diff, and stops the task.

advisory

Written in the session summary, a brief or a role card. The model can ignore it.

6. Classification Ratchet

The model proposes a class. Code watches what is really touched and can only raise it. Only a typed command from the human lowers it.

questionNo record, no ceremony. Reading is free.
trivial_editOpened automatically on the first edit. Lead does it. Small budget.
standardProfile, plan, worker, checks recorded by code.
high_riskYour click for each protected file, stronger validator, human settles disputes.

Signals that raise the class

  • declared by the model, including sensitivity flags (auth, payments, data migration, deployment, secrets). Works in any language because the model reads the meaning. Can only raise.
  • planned paths in the plan's scope.
  • observed paths, diff size and command class from hooks. The strongest signal.
  • No keyword matching in code.

Example: a misjudged change

"Small tweak to the login timeout." The lead calls Edit on src/auth/session.ts. The path matches **/auth/**, so the class jumps to high_risk and the edit is denied before it happens. Cost of the wrong guess: one denial, not an unreviewed change.

trivial_edit budget agreed

  • Max 2 files, 40 changed lines.
  • Max 1 new file, no deletions.
  • Bash: read, checks, local git.
  • Over budget → standard; changes stay.

Protected paths agreed

high_risk: auth/ security/
  migrations/ .env* *secret*
  .github/workflows/ Dockerfile*
  terraform/ k8s/
standard: package.json
  requirements*.txt *.lock
never: approvals, ledger,
  .claude/settings*, hooks.json

Projects can add paths, never remove from never.

Lowering and git agreed

  • Class only goes up. Lowering is a typed human command, recorded.
  • Hard gates can't be lowered.
  • Scope can widen twice per task, unprotected paths only.
  • Edits need git. No git → read_only.

7. Routing

A role is a card injected into a subagent. The tier is picked by a written rule, never by asking a model how hard the task feels.

Rule table · defaults/rules.yaml

route:
  read_logs | search | inventory → fast
  trivial_edit                   → lead itself
  scoped_bugfix | tests | docs   → balanced
  feature | debugging            → frontier
  security_review                → frontier
  architecture | migration       → deep
validator_tier:               # by assurance
  low → checks by code only
  medium → balanced
  high → frontier
guards:
  code_edits: never on fast
  workers: cannot spawn agents
  one writer at a time
  built_in_agents: Explore, Plan only

Two separate axes

  • change_risk: how dangerous the action is. Drives the gate and approvals.
  • assurance: how costly a wrong conclusion is. Drives evidence and the validator.
  • A security audit changes nothing (low risk) but needs high assurance.
  • The validator tier follows assurance, not the worker's tier.
Haikufast

Search, extraction, log reading. Never edits code.

Sonnetbalanced

Scoped fixes, tests, docs, routine validation.

Opusfrontier

Features, debugging, security review.

Fabledeep

Architecture, migrations. Falls back to Opus if unavailable.

8. Approvals

The model can ask. Only the human can answer, with a click in Claude Code's own Allow/Deny prompt, which shows the real action. agreed · D46 · built in phase 3

Sequence

  1. modelTries git push origin fix/session.
  2. gateWrites a request from the real tool input, with branch and outgoing commits, and returns ask.
  3. humanSees the exact command in Claude Code's prompt and clicks Yes or No.
  4. hookThe command ran, so it was allowed: the record becomes approved by human, with the commit actually pushed.
  5. gateThe next push asks again.

Approval record

approval_id: APR-afc3aa21
kind: action
action: "git push -u origin fix/session"
command_class: vcs_remote
task_id: TASK-001
context: { branch: main, outgoing_commits: [...] }
decision: approved
decided_by: human   # set by the hook
method: native_prompt
context_after: { head: d7701ec }
KindCoversHow the human answersValid for
ActionPush, publish, network, destructive, unknown command in a high_risk taskYes / No in Claude Code's promptThat one run; the next asks again
Protected fileFirst edit of each protected file in a taskYes / No in Claude Code's promptThat file, until the task closes, max 24 hours
DecisionA violation, a step blocked after 3 attempts, a dispute for the user, an amendment in high_risk, closing a high_risk task, using FableTyped /engos:decide TASK-… <option>That decision only

Every mode verified

The prompt appears in default, auto and bypass, even when a settings rule allows the command. Headless turns it into a denial.

No blanket approvals agreed

No "approve every push in this task" in v0.1. Each external action gets its own click.

Records can't be forged built

Hooks keep a fingerprint of every approval record. A record written or changed by anything else stops the task.

Typed commands remain only for decisions, lowering a class and pause. A script can fake a typed command (spike R8) and --resume keeps the session id (P9), so they count only from the task's own session, not after it was resumed, and Bash may never run claude (D34, D35).

9. Failure and Escalation

Not every failure means a bigger model will help. The type of failure picks the response.

FailureResponseCounts as a cycle
check_failedRetry same tier with the exact output, then one tier upyes
env_errorBack to the lead, then the human. Missing dependency, flaky tool.no
scope_violationReclassify through the ratchetno
criterion_disputedDispute rules in section 10no

Three attempts per step agreed

Routed tier, then the same tier with the exact failing output, then one tier up. Sonnet → Sonnet → Opus → human. Fable is only reached when the human picks it.

Who labels a failure agreed

Code labels exit codes and missing tools. The lead labels the rest. Two env_errors in one step go to the human, so the label can't be used to dodge the count.

Uncertainty as checks agreed

A hypothesis exists, quoted log lines exist verbatim, all symptoms are explained. Evidence across more than one component goes one tier up.

After the last attempt the task is blocked and the human gets a handover: what was tried, current state, options and the lead's recommendation.

10. Who Is Responsible

The lead owns the outcome of the task. A subagent owns its step. The human owns acceptance and anything that leaves the repo. agreed

Lead does it vs delegates

question, trivial_editLead does it
Steps in standard and high_riskWorker
Heavy readingScout
Intake, plan, talking to the humanAlways the lead
Small fix after a workerLead, within a small budget

Who settles a disagreement

A check failedNobody. It's a fact.
Judgement call, standardLead, once per task, recorded
Judgement call, high_riskHuman
Security finding ≥ mediumHuman

The lead can never: skip a failed check, change acceptance criteria without a recorded amendment, mark a task complete, grant an approval, or lower a class.

11. The User Always Sees and Decides

Agents work in the background, so their work has to stay visible. And not every subscriber has every model, so the expensive tier is the user's call. built in phases 5 and 6

Status line

One line under the prompt: task, class, each agent with its model and step, attempts, approvals waiting.

Live graph · /engos:view

Local page that refreshes every 2 seconds from .engos/status.json: agent graph, steps, timeline, evidence, what's waiting for you. In the Desktop app it runs through a small read-only server on 127.0.0.1. It can't approve anything.

Text · /engos:status

The same picture printed in the chat, for when the page isn't open.

Model availability

Asked once and saved in .engos/config.yaml. If a call fails because a model isn't on the user's plan, it's marked unavailable and the step falls back one tier, with a note.

Fable needs a yes

When a step routes to the deep tier, the gate stops the agent call, the lead explains why, and the user types /engos:decide TASK-… fable or no_fable. No means Opus. If the plan lacks Fable, nobody is asked.

Key takeaways
  • A plugin, because hooks are the only part that can stop a tool call.
  • Built to catch mistakes and injected instructions, and says so. Not a sandbox.
  • Class comes from what the code touches, and only goes up.
  • Small work costs nothing extra; the lead does it directly.
  • Evidence is recorded by code, and only the human can approve.
  • Cheaper on reading: big jobs go to a Haiku scout, questions search before reading (measured: −44% documenting a project, −14% analysing a real 193-file project; code changes +2–19% for the plan and evidence steps).
